What Docker is, and how this lab uses it

image · container · compose

A container is a process with its own filesystem and network, started from a read-only image. In this course that is how the database lab gets Postgres and pgAdmin — one docker compose up, no local install.

From a recipe to a running lab

Lab stack — cd db && docker compose up

services:
  db:
    image: postgres:16
    ports: ["5432:5432"]   # host:container
    volumes: [pgdata:/var/lib/postgresql/data]
  pgadmin:
    image: dpage/pgadmin4
    ports: ["5050:80"]
    environment:
      PGADMIN_DEFAULT_EMAIL: admin@example.com
      PGADMIN_DEFAULT_PASSWORD: admin
volumes:
  pgdata:

Your own app — build an image, then run it

# Dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
CMD ["node", "agent.js"]

# shell
docker build -t lab-agent .
docker run --env-file .env lab-agent
docker compose ps
docker compose logs -f db
docker compose down       # keeps pgdata

A container is not a second laptopIt is a Linux process with its own files, network stack, and process list, cut off from the rest of the machine. On macOS, Docker Desktop hides a small Linux VM and forwards the ports you publish. You still do not install Postgres yourself.

Left is the host, right is the container5050:80 means the browser’s localhost:5050 reaches port 80 inside pgAdmin. On the compose network, containers call each other by service name — db:5432 — not by the laptop’s localhost.

The image stays cleanWrites inside a container sit on a thin layer that disappears with the container. The named volume pgdata is outside that layer, so docker compose down keeps the database. Add -v only when you mean to delete it.
